# Agent Lab v1.4 Local Claim Evaluation Pilot

- 状态：第一阶段已完成；公开文档 pilot 已按当前源码与运行证据校正为私有 draft，人工独立复核待完成（2026-08-13）
- 目标：为真实但公开或已授权语料建立可审计、可人工复核并冻结的 claim-level 基准
- 非目标：本阶段不运行 Provider、claim extractor、entailment checker，不比较模型，不改 v1.3 oracle suite

## 决策

v1.3 继续只证明 RAGChecker 指标内核在合成 oracle label 上可重算。v1.4 使用独立的私有 suite root，把真实语料评测中最先需要稳定的输入固定下来：corpus、query、ground-truth claim、精确 evidence span、answerability、类别、split 与人工裁决状态。

私有 suite 默认放在 `~/.agentlab/evals/<suite-id>/`，但 CLI 只接受用户显式传入的路径，不隐式扫描用户目录。原文与 Gold 不进入仓库、发行包、trace 或公共错误。suite root 和子目录必须为 `0700`，文件必须为 `0600`，所有成员必须是普通文件或目录且不得包含符号链接。

## 目录与契约

```text
<suite-root>/
├── manifest-v1.json
├── cases-v1.json
└── corpus/
    └── **/*.md|*.txt
```

`manifest-v1.json` 严格包含：

- `schema_version=1`、kebab-case `suite_id`、正整数 `suite_version`
- `status=draft|frozen`
- `provenance=public|authorized_private`
- `source_snapshot`：最长 160 字符的 public-safe ASCII 标识，只允许小写字母、数字、点、下划线和连字符；至少编码来源 revision 或工作树基准与捕获日期，不得含路径、原文或凭据
- `annotation_protocol_version=local-claim-annotation-v1`
- `corpus.directory=corpus`、规范化 corpus hash、`chunk_size`、`overlap` 与 chunk-set hash
- `cases.file=cases-v1.json` 与 cases 文件逐字节 hash

`draft` 可暂时把三项 hash 写成字符串 `pending`；validator 仍会重算并在不含原文的报告中返回实际值。转为 `frozen` 前必须将实际 hash 填回 manifest，`frozen` 不接受 `pending`。

`cases-v1.json` 严格包含 `schema_version=1` 和 cases。每个 case 固定 `id`、`split`、`category`、`query`、`answerability`、`adjudication_status`、`review` 和 `ground_truth_claims`。`review` 分别记录首轮复核、独立复核和可选裁决备注；报告不得输出备注。每条 claim 固定唯一 ID、原子 proposition 文本和至少一个精确 evidence span。offset 是对换行规范化为 `\n` 后 Python 字符串的半开区间 `[start,end)`，不是 UTF-8 byte offset。

校验器以有界 no-follow 方式读取 JSON，重算三组 hash，并验证每个 evidence span 逐字符匹配 source、完全落入一个确定性 chunk、case/claim ID 在 suite 内全局唯一、query 经空白归一化与 casefold 后唯一、split/category 合法以及 answerability 与 Gold 形状一致。输出只含 suite ID、状态、来源类型、脱敏 snapshot 说明、计数、类别、split 与 hash。

## 人工标注规范

1. Query 必须来自预先定义的用户任务，不因当前检索或回答结果改写。语义等价改写可作为独立 case，但不得复制到 calibration 与 holdout 两侧。
2. Claim 只表达一个可独立判真的事实。并列事实、多个数字、条件与结论要拆开；不为使系统得分更高而合并或删除 claim。
3. Evidence 必须是 source 中足以支持 claim 的最小连续 span。多个来源独立支持同一 claim 时可记录多个 span；缺少直接证据的事实不得进入 Gold。
4. `answerable` 至少一条 Gold；`unanswerable` 必须零 Gold；`conflicting` 至少两条 Gold 且覆盖至少两个来源，claim 文本分别陈述各来源的冲突内容。
5. 无法稳定判断原子性、answerability 或证据充分性时使用 `answerability=unclear` 或 `adjudication_status=needs_review`。不得猜测；这些 case 不能进入 frozen suite。
6. 数字、日期、否定、范围词、比较级、条件与实体指代必须逐字核对。对“支持大意但缺少限定”的 pair 不标 entailed。
7. 第一位标注者完成后，第二轮只看规范与原始材料独立复核。分歧写回 case 并裁决为 `adjudicated`；validator 只能证明裁决已记录，不能证明裁决语义正确。
8. `conflict` 只用于同一对象、同一时间和同一条件下无法同时为真的来源陈述。带明确日期的旧状态与后来状态属于时间演进；应把时间写进 query/claim，并标为 `multi_document` 或 `numeric_temporal`，不得为满足类别覆盖而伪造冲突。
9. Agent 可以用当前源码、fixture、CLI 和本地离线运行核验草稿是否符合项目现状，并把依据写入不对外输出的备注；这种事实核验不是人工独立复核，不能设置 `independent_reviewed=true`。

## 冻结门槛

`draft` 用于逐步标注，可包含 `needs_review` 或 `unclear`。`frozen` 必须同时满足：

- 至少 24 个唯一 query，calibration 至少 16 个、holdout 至少 8 个
- `single_document`、`multi_document`、`numeric_temporal`、`negation`、`unanswerable`、`bilingual_rewrite` 每类至少 1 个 case
- `conflict` 是允许但按 corpus 条件触发的类别：只有存在真实同范围冲突时才要求覆盖；无冲突 corpus 不得构造假冲突
- 全部 case 为 `adjudicated`，首轮与独立复核均已记录，不存在 `unclear`
- manifest 中 corpus、cases 与 chunk-set hash 全部匹配

修改 corpus、case、Gold、span、chunking 或 split 后，旧 manifest 必须失效；若要重新冻结，提升 `suite_version` 并重新计算 hash。holdout 在后续选定 extractor/checker 的 prompt、模型和阈值后只用于最终评测，不参与调参。

## 当前 Pilot

当前本机私有 pilot 使用 Agent Lab public-safe 文档的本地授权快照，不读取求职材料或其他私人输入。snapshot 基于公开 v1.3 revision `13bffd698b24b9ab23b3de7f887f9267174b49a3`，并包含 2026-08-13 捕获的本地 v1.4 README 草稿；后续 README 措辞校正不回写这份已绑定 hash 的历史快照。因此 manifest 明确标为 `authorized_private`，不能表述为逐字节公开 revision 或当前工作树镜像。它包含 25 个 query（calibration 16 / holdout 9）、6 个冻结必需类别、39 条草拟 claim 和 39 个精确 span；schema、权限、span 与三组 hash 已通过 validator。语料没有发现同范围事实冲突，因此不包含 `conflict` case。

25 个 case 已逐项回到当前源码、fixture、CLI 或可重算报告核验，并在私有备注中记录核验依据。原 `public-status-document-conflict` 把 2026-07-31 的历史“实施中”与后来 README 的发布状态误标为冲突，现已改成明确日期边界的多文档状态演进问题。此前由维护者确认且内容未实质变化的 8 项保留 `primary_reviewed=true`；其余项因 query、claim 或 evidence 改写，或此前未审核，均保持未首轮复核。全部 case 仍为 `independent_reviewed=false`、`needs_review`，因此报告必须为 `status=draft`、`frozen_ready=false`。这些草拟标签不能称为人工 Gold，也不能进入 extractor/checker 或端到端质量结论。人工复核若修改任何 query、claim、span 或 split，需重算 cases/chunk/corpus hash 后再冻结。

## 后续阶段

第二阶段新增带人工 response-claim 边界的运行快照，单独评估 extractor 的遗漏、错误切分和多事实合并。第三阶段建立四个方向的人工 pair bank，以 `entailed/not_entailed/unclear` 评估 checker，重点报告 false positive 以及数字、否定、条件、冲突切片。两者通过预先批准的 holdout 门槛后，才用自动矩阵比较固定生成器下的 retrieval、固定 context 下的 generation 与端到端系统。

任何真实 Provider 调用都需要单独授权费用与数据外发，运行前明确列出会发送的 query、claim、chunk 和 response 字段。本地契约通过不能表述为自动评测可靠、真实 RAG 质量提升或线上监控已完成。
